# Hermes 主控助理企業級優化計劃書

> **For Hermes:** 本文件用於企業級、可審計、可維運、可回滾的系統優化。請依據此計劃逐項實作與驗證。

**目標**：將 Hermes 建構為一套穩定、低風險、低 token 成本、可追蹤、可持續維運的工業級主控系統。  
**架構**：採用「感知層 → 規則層 → 判斷層 → 執行層 → 記錄層」五層式架構。高頻、明確、可驗證的工作交由規則與程式處理；模糊、需要語意理解或策略整合的工作才交由模型。  
**適用範圍**：系統管控、定時盯盤、Binance 交易輔助、通知、復盤、文件化與長期維運。

---

## 1. 執行摘要

Hermes 的優化方向不是增加聊天能力，而是提升「任務完成率、風險控制力、可追溯性與長期穩定性」。

本計劃的核心要求如下：

- **穩定優先**：任何優化都不能破壞既有可用能力。
- **規則優先**：可規則化的工作一律不依賴模型。
- **低 token 成本**：高頻盯盤、改單與健康檢查不得依賴長對話決策。
- **可回滾**：每次關鍵變更都應保留備份與驗證步驟。
- **可審計**：交易、改單、策略變更與系統調整都必須留下紀錄。
- **可持續**：系統要能長期運作，而不是只在單次任務中表現良好。

## 2. 現況評估

### 2.1 已具備能力
- 已有 Raspberry Pi 主控環境。
- 已有 Binance quant control plane。
- 已有交易分析、報告生成與狀態檔案機制。
- 已有 Telegram 通知與部分自動化流程。
- 已具備可支援系統健康檢查與本地服務監控的工具鏈。

### 2.2 主要痛點
1. **高頻動作仍可能消耗不必要 token**。
2. **盯盤與風控規則尚未完全標準化**。
3. **倉位大小與風險暴露仍需更清楚量化**。
4. **復盤閉環需要更固定的輸出格式**。
5. **系統與交易職責邊界需進一步分離**。

### 2.3 風險判斷
- 若策略判斷仍高度依賴自然語言互動，會導致不穩定與成本上升。
- 若倉位管理未標準化，帳戶會因過度波動而失去可持續性。
- 若變更沒有備份與驗證，系統長期維護成本會快速上升。

## 3. 企業級設計原則

### 3.1 基本原則
- **穩定優先於速度**。
- **可回滾優先於一次到位**。
- **規則優先於主觀判斷**。
- **小步調整優先於大改架構**。
- **有證據的決策優先於記憶中的印象**。

### 3.2 交易原則
- 每筆交易必須在開倉時就帶有止損與止盈。
- 倉位大小以「停損後的風險」為主，不以槓桿表面數字為主。
- 小帳戶以生存率與穩定成長為第一優先。
- 高品質訊號才允許更高風險暴露。
- 每筆交易都應能被復盤、歸因與優化。

### 3.3 自動化原則
- 高頻監控交由規則引擎。
- 模型只處理模糊、例外、整合型判斷。
- 當規則足夠明確時，不應叫模型重算。
- 當市場狀態變化不大時，不應重複消耗 token。

## 4. 目標架構

### 4.1 五層架構

#### A. 感知層
負責收集原始資料：
- 持倉
- 掛單
- 市價
- K 線
- 技術指標
- 新聞
- whale 資訊
- 系統健康狀態

#### B. 規則層
負責做明確決策：
- 是否移動止損
- 是否鎖利
- 是否減倉
- 是否暫停交易
- 是否發通知

#### C. 判斷層
負責處理模糊情境：
- 趨勢是否延續
- 是否進入轉折期
- 是否該續抱或退出
- 多訊號整合判斷

#### D. 執行層
負責實際操作：
- Binance 下單 / 改單
- Telegram 通知
- 檔案寫入
- 狀態更新

#### E. 記錄層
負責保存歷史與證據：
- 交易紀錄
- 風控紀錄
- 變更紀錄
- 週報 / 月報
- 復盤摘要

## 5. 倉位分級標準

### 5.1 名詞定義

#### 小倉
用途：試單、探路、驗證訊號。  
特徵：虧損可承受，不影響整體節奏。  
適用：趨勢未完全確認、波動高、容易假突破、流動性較差的標的。

#### 中倉
用途：標準出手。  
特徵：策略已確認後的常規交易規模。  
適用：趨勢明確、結構完整、風報比合理的情境。

#### 大倉
用途：放大高品質優勢。  
特徵：對帳戶波動影響顯著，風控要求最高。  
適用：高共振、高延續、高信心、高流動性場景。

### 5.2 企業級判斷邏輯
倉位大小不應由「顆數」或「槓桿」單獨決定，而應由以下因素綜合判定：
- 帳戶總資金比例
- 單筆最大虧損
- 停損距離
- 波動率
- 流動性
- 市場結構
- 策略信心分數

### 5.3 建議操作語義
- **探路倉**：最小試單。
- **標準倉**：策略正常執行的主力倉位。
- **加強倉**：僅在極高品質訊號時使用。

## 6. 核心功能範圍

### 6.1 盯盤自動化
需求：
- 持續監控持倉與掛單
- 監控是否接近止盈或止損
- 根據規則自動調整停損
- 依條件發出提醒
- 避免重複判斷與重複通知

### 6.2 風控引擎
需求：
- 計算 R 倍數
- 管理最大風險敞口
- 限制單筆與總體回撤
- 對過度波動情況進行保護
- 避免盲目加倉或攤平

### 6.3 策略判斷
需求：
- 整合技術面、新聞面、whale 面
- 對模糊市場做最終解讀
- 區分「規則可決定」與「需模型協助」

### 6.4 復盤系統
需求：
- 記錄入場理由
- 記錄出場理由
- 記錄是否符合策略
- 記錄是否需要參數修正
- 將每筆交易轉成可學習資料

### 6.5 文件化系統
需求：
- 用 `.md` 文件記錄計劃、報告與復盤
- 用 `.json` 保存狀態與快照
- 讓每次變更可審查、可追蹤、可回滾

## 8. 實作里程碑

### Milestone 1：規則層固定化
**目標**：把可規則化決策全部寫成明確條件。

交付物：
- 倉位分級規則
- 1R / 2R / trailing 規則
- 暫停交易條件
- 通知條件

驗收：
- 不需要模型即可執行高頻監控
- 規則能穩定重複執行

---

### Milestone 2：風控引擎標準化
**目標**：將風險控制從手工決策提升為系統化流程。

交付物：
- 最大單筆風險上限
- 最大總體風險上限
- 自動保本規則
- 自動鎖利規則

驗收：
- 每筆交易都能被量化風險
- 出現高波動時能自動保護帳戶

---

### Milestone 3：盯盤與改單自動化
**目標**：把盯盤從人工過程變成穩定服務。

交付物：
- 持倉監控器
- 條件式改單器
- 異常中止機制
- 通知去重機制

驗收：
- 不需反覆問模型
- 改單流程可追蹤

---

### Milestone 4：復盤閉環
**目標**：讓每筆交易都可學習。

交付物：
- 交易復盤模板
- 每日摘要
- 每週策略回顧
- 參數調整提案

驗收：
- 策略會隨交易結果更新
- 不是單次輸贏，而是系統演進

---

### Milestone 5：文件與維運制度化
**目標**：讓系統具備長期維護性。

交付物：
- 變更紀錄
- 備份規則
- 健康檢查規則
- 故障回復手順

驗收：
- 任何關鍵變更都留痕
- 可快速定位與回復問題

---

## 9. 驗收標準

### 技術驗收
- 高頻盯盤可不依賴自然語言互動
- 設定變更可回滾
- 重要行為有日誌與檔案證據
- 系統服務狀態清楚
- 自動通知正常

### 交易驗收
- 每筆交易有明確止損 / 止盈
- 倉位大小有一致標準
- 風險暴露可量化
- 復盤能導出具體改進建議

### 維運驗收
- 文件可查
- 狀態可追蹤
- 故障可回復
- 變更有記錄

---

## 10. 風險管理

### 10.1 主要風險
1. 模型使用過度，造成 token 浪費。
2. 交易倉位過大，破壞帳戶穩定性。
3. 自動化流程缺乏回滾，導致維護困難。
4. 變更沒有標準紀錄，造成資訊斷裂。
5. 規則不清，使系統與對話混在一起。

### 10.2 緩解策略
- 盡量把高頻動作規則化。
- 對風險暴露設硬上限。
- 所有重要變更先備份。
- 所有重要結果寫檔留痕。
- 模型只處理規則無法穩定處理的部分。

## 13. 結論

Hermes 的企業級優化，不是讓它更會講話，而是讓它：

- 更穩定
- 更可控
- 更低 token 成本
- 更適合長期維運
- 更容易進行交易與系統決策
- 更容易復盤與持續優化

**最終目標**：讓 Hermes 成為一個可以長期信任的主控系統，而不是一次性工具。

---

## 14. 推進順序建議

1. 先規則化高頻盯盤與風控
2. 再標準化倉位分類
3. 再建立復盤閉環
4. 再補齊文件與維運制度
5. 最後才擴展更複雜的策略能力

**原則**：先穩，再快；先可控，再擴張；先規則，再模型。
