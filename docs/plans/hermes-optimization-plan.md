# Hermes 主控助理優化計劃書

> **目的**：將 Hermes 優化為一個更穩定、更可維運、可審計、低 token 成本、可自動化執行的工業級主控助理。

**版本**：v1.0  
**撰寫日期**：2026-04-27  
**適用場景**：Raspberry Pi 主控、Binance 量化工作流、系統診斷、定時盯盤、通知、文件化與長期維護

---

## 1. 專案目標

### 1.1 核心目標
把 Hermes 從「能回答問題的 AI」升級成「能穩定完成任務的主控系統」。

### 1.2 具體目標
1. **降低人工介入成本**：盡量由規則與自動化完成可重複工作。
2. **降低 token 消耗**：把高頻、明確、可規則化的動作從模型層移出。
3. **提升可靠性**：重要行為要可驗證、可回滾、可追蹤。
4. **提升交易工作流品質**：交易前、交易中、交易後都有固定流程。
5. **強化工業級穩定性**：避免臨時手工操作取代系統化流程。
6. **建立長期記憶與操作紀錄**：讓系統越用越穩，而不是每次重來。

## 2. 當前問題定義

### 2.1 現況優勢
- 已具備明確的主控風格與工具鏈。
- 已有 Binance quant control plane。
- 已有交易分析、監控、通知與部分自動化能力。
- 已有可用的本地服務與資料檔案結構。

### 2.2 主要問題
1. **規則與模型邊界仍需更清晰**
   - 哪些要自動做，哪些要問模型，界線要更明確。
2. **高頻盯盤容易浪費 token**
   - 若每次變動都問模型，成本高且不穩定。
3. **交易決策與風控流程需要更標準化**
   - 止盈、止損、移動停損、加減倉需要固定規則。
4. **計劃書、報告、復盤格式尚未完全模板化**
   - 難以一致化輸出。
5. **系統層與交易層的責任分離可再強化**
   - 避免主控邏輯混雜在臨時對話中。

## 3. 設計原則

### 3.1 工業級原則
- 穩定優先於炫技。
- 可回滾優先於一次到位。
- 可審計優先於黑盒決策。
- 規則優先於模型，模型只處理模糊問題。
- 高頻動作自動化，低頻決策保留人工/模型介入。

### 3.2 交易原則
- 每筆交易都必須有止損與止盈。
- 風險以停損金額衡量，不以表面槓桿衡量。
- 小帳戶以存活率為第一目標。
- 只有高品質訊號才允許更大倉位。
- 每筆交易都要做事後復盤並沉澱規則。

### 3.3 token 原則
- 讀資料、算條件、改單：盡量零 token。
- 只有需要主觀判斷時才用模型。
- 長篇報告只在必要時生成。
- 高頻監控不應依賴對話式判斷。

## 4. 系統架構目標

### 4.1 分層架構

#### A. 感知層
負責收集：
- 持倉
- 掛單
- 價格
- 技術指標
- 新聞
- whale 資料
- 系統健康

#### B. 規則層
負責：
- 自動判斷是否移動止損
- 自動判斷是否鎖利
- 自動判斷是否減倉
- 自動判斷是否停止交易
- 自動判斷是否通知

#### C. 模型層
負責：
- 盤勢模糊時的最終判斷
- 特殊情況的語意整合
- 交易後歸因與教訓整理
- 長篇報告生成

#### D. 執行層
負責：
- Binance 下單 / 改單
- Telegram 通知
- 檔案寫入
- 記錄日誌
- 狀態快照

## 5. 優化範圍

### 5.1 盯盤系統優化
目標：讓系統能持續監控倉位並自動處理風控事件。

包含：
- TP / SL 監控
- 1R、1.5R、2R 規則
- 波動擴大時調整停損距離
- 突破失敗時提早保護收益
- 低流動性或高風險行情暫停操作

### 5.2 倉位管理優化
目標：讓大小倉判斷標準化，而不是憑感覺。

包含：
- 小倉 / 中倉 / 大倉定義
- 每筆交易風險上限
- 不同帳戶規模的倉位模板
- 加倉與減倉規則

### 5.3 交易復盤優化
目標：每一筆交易都變成可重複利用的知識。

包含：
- 進場原因
- 出場原因
- 訊號是否共振
- 風報比是否合理
- 是否需要調整參數

### 5.4 報告與文件化優化
目標：所有重要行為都形成可讀、可追蹤的 md 文檔。

包含：
- 日報
- 交易報告
- 風控報告
- 系統變更紀錄
- 問題處理紀錄

### 5.5 記憶與知識庫優化
目標：把穩定做法沉澱成可重用知識。

包含：
- 長期偏好
- 穩定操作流程
- 交易策略規則
- 系統限制與例外處理

## 6. 小倉 / 中倉 / 大倉定義

### 6.1 交易員視角的定義

#### 小倉
- 用途：試單、探路、驗證方向
- 特徵：虧損可忽略，不影響整體節奏
- 適用場景：新幣、假突破高、趨勢未完全確認

#### 中倉
- 用途：標準出手
- 特徵：策略確認後的主力規模
- 適用場景：趨勢清楚、結構穩定、風報比合理

#### 大倉
- 用途：核心優勢放大
- 特徵：對帳戶影響明顯，風控要求最高
- 適用場景：高共振、高信心、高延續行情

### 6.2 實務判斷標準
不要只看幣數或槓桿，而要看：
- 停損後虧多少 USDT
- 這筆交易占總資金比例
- 波動率多大
- 是否容易滑點
- 是否容易假突破

### 6.3 建議分級方式
- **小倉**：用來試錯，單筆停損小
- **中倉**：日常主力倉位
- **大倉**：只在高品質機會使用，且需更嚴格監控

## 7. 功能設計

### 7.1 自動盯盤模組
功能：
- 監看持倉與掛單
- 檢查價格是否接近 TP / SL
- 依規則調整停損
- 必要時發出通知

### 7.2 風控引擎
功能：
- 計算 R 倍數
- 計算風險暴露
- 設定最大風險上限
- 防止過大倉位或重複開倉

### 7.3 策略分析模組
功能：
- 整合技術面、新聞面、whale 面
- 輸出簡潔決策摘要
- 只在需要時升級為模型判斷

### 7.4 復盤引擎
功能：
- 記錄每筆交易的事前條件與事後結果
- 自動生成復盤摘要
- 建議下一步參數調整

### 7.5 文件輸出模組
功能：
- 產出 `.md` 計劃書
- 產出 `.md` 復盤報告
- 產出 `.json` 狀態快照
- 產出 Telegram 短報告

## 8. 執行路線圖

### Phase 1：規則清晰化
**目標**：先把規則與模型責任邊界切乾淨。

任務：
1. 定義哪些動作完全規則化
2. 定義哪些情況才需要模型判斷
3. 定義哪些動作必須通知
4. 定義哪些動作必須寫檔

驗收：
- 高頻盯盤不需要反覆問模型
- 每個動作有明確責任層

---

### Phase 2：倉位與風控標準化
**目標**：讓每筆交易有一致的倉位語言。

任務：
1. 定義小倉 / 中倉 / 大倉
2. 定義最大單筆風險比例
3. 定義 1R / 2R / trailing 規則
4. 定義加倉與減倉規則

驗收：
- 可根據帳戶大小自動推導倉位等級
- 每筆交易的風險可被量化

---

### Phase 3：盯盤自動化
**目標**：把調止盈止損變成機器可執行流程。

任務：
1. 寫出倉位監控規則
2. 寫出條件式改單規則
3. 寫出通知規則
4. 寫出異常中止規則

驗收：
- 能自動追蹤行情與倉位
- 不必每次都人工介入

---

### Phase 4：復盤與學習閉環
**目標**：每筆交易都能回饋到下一筆交易。

任務：
1. 每筆交易記錄進場原因
2. 每筆交易記錄出場原因
3. 每筆交易記錄是否符合策略
4. 每週整理一次參數調整建議

驗收：
- 系統能累積知識
- 策略能持續微調而不是亂改

---

### Phase 5：文件化與長期維運
**目標**：把系統從「能跑」升級成「能長期維持」。

任務：
1. 建立固定 md 模板
2. 建立狀態快照模板
3. 建立變更紀錄模板
4. 建立健康檢查與備份流程

驗收：
- 每次重要變更都能追蹤
- 問題可回溯、可重現、可修復

## 10. 風險與緩解

### 10.1 風險：模型介入過多
**緩解**：
- 規則先行
- 模型只處理模糊區
- 高頻流程全部程式化

### 10.2 風險：倉位過大
**緩解**：
- 以停損金額而非槓桿判斷風險
- 設定每筆交易最大風險比例
- 使用小倉先驗證

### 10.3 風險：盯盤頻繁導致 token 浪費
**緩解**：
- 使用本地規則引擎
- 只在重大條件變化時呼叫模型

### 10.4 風險：狀態遺失或變更不可追蹤
**緩解**：
- 每次變更寫檔
- 重要檔案先備份
- 交易與系統操作留痕

## 13. 結論

Hermes 的優化方向，不是變成更會聊天，而是變成：

- 更穩
- 更少 token
- 更容易驗證
- 更能自動執行
- 更適合長期持續運作

真正專業的主控助理，不是每次都做很多話，而是每次都做對事。
